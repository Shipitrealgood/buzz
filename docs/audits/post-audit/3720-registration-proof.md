### H-1 — Pruning permanently rejects every fresh host mailbox snapshot

**Measured.** The unmodified production DB APIs accept a signed claim/ack and a fresh `messages` read. Aging one synthetic transient row's `received_at`, then posting a second normal signed query, runs the real pruning implementation and raises `retention_floor` to 3. Both subsequent null-cursor reads return `PairedCursorPruned`. [Probe source](../../verification/3720/review/pruning-probe.rs), [receipt](../../verification/3720/review/pruning-probe.txt).

**Read.** `crates/buzz-db/src/store/paired_hosts/registry.rs:218` converts absence of a cursor to position 0; `:223` rejects any position below the permanent retention floor. `paired_hosts/phases.rs:178` starts pruning v2 transients after five minutes. `crates/buzz-hostd/src/registration.rs:359` always starts reconciliation with a new null-cursor `messages` query and `:364` propagates its failure; the constructor at `:303` supplies no alternate starting position. The opaque WS adapter cannot mint a continuation when the first page fails.

**Failure:** an offline host leaves an unanswered readiness query; after five minutes another query prunes it. That generation can no longer reconcile its active mailbox, even after reconnect/restart. Ordinary answered queries also become prunable once superseded. Binding-only revocation can still work; this is not a claim that local restrictive revocation is lost. It violates P10/P11's explicit reset/recovery obligation and P2's ability to establish fresh readiness after recovery ([spec](../../specs/3720-host-registration-event-proof.md), §§5–6,8).

**Root-level recommendation:** distinguish a fresh retained-state snapshot from an incremental continuation. A null cursor can enumerate retained rows under a new snapshot while stale continuation tokens still require explicit resync; preserve consent/revocation evidence and bounded pages. Alternatives: issue a new authenticated reset cursor with an explicit completeness contract (more protocol machinery), or disable pruning (reject: violates bounded mailbox retention). Merely retrying null forever, clamping every old cursor silently, or raising retention does not repair the contract. Regression must age real synthetic rows, invoke production pruning, then drive root WS + `Host::reconcile` to a fresh nonce response; also reject an actually stale continuation and recover without losing restrictive evidence.

### H-2 — Async reconciliation uses stale local time for first proof consumption

**Read.** `crates/buzz-hostd/src/registration.rs:295` receives one clock snapshot, then awaits offers and exact evidence before calling `self.claim(g, &e, clock)` at `:332`. It likewise reuses that clock for message expiry and `receive` at `:374,390`. `claim` checks wall/boot/monotonic expiry at `:101` and signs the ack using `clock.wall` at `:141`; the checks therefore use time from before the network work. The existing clock supplies `refresh()` at `clock.rs:17`. The v1 transport already reads fresh time after network waits (`transport.rs:255,280,423`).

**Failure:** reconciliation starts just before invitation expiry; the evidence response arrives after the local deadline. First consumption still succeeds using the captured time, and its backdated ack looks timely to the relay's deliberately permitted 24-hour delivery retry. The relay cannot decrypt the proof and must rely on hostd for first-consumption expiry. This violates P6, not merely a UI freshness preference. Stale time can also extend local processing of readiness queries across awaited pages.

**Measured probe:** the existing injectable `Clock.source` reports wall/monotonic time beyond expiry after the initial snapshot, while real root WS offers/evidence are fetched. The production reconcile path creates an ACTIVE local grant and a live relay binding instead of refusing first consumption. [Temporary test](../../verification/3720/review/clock-probe.rs), [receipt](../../verification/3720/review/clock-probe.txt), [restoration hashes](../../verification/3720/review/clock-probe-hashes.json). This is a deterministic injected-clock experiment, not a 10-minute real-time sleep.

**Fix:** use the existing refresh source immediately before clock-sensitive local checks/transactions and after network waits. Keep exact saved-ack replay distinct from first consumption, and retain restrictive revocation's rollback behavior. Extend P6 with the delayed-fetch expiry case, rollback/boot change after await, and an exact timely ack retry that remains allowed.

### M-1 — An older failed REQ retires its newer same-ID replacement

**Measured.** The authorized temporary test holds the existing DB admission lock, calls production dispatch for an older nonexistent binding read, waits for owner token 1, dispatches a new live REQ under the same subscription ID, and observes owner token 2. Releasing the lock yields `CLOSED` from the old failure and removes token 2. The new live snapshot never arrives. Exactly one assertion fails, with no product mutation. [Probe](../../verification/3720/review/replacement-probe.rs), [failure receipt](../../verification/3720/review/replacement-probe.txt), [restoration hashes](../../verification/3720/review/replacement-probe-hashes.json).

**Read.** `crates/buzz-relay/src/handlers/host_registry.rs:526` claims an owner token, but `read(...).await?` at `:545` and reply errors escape to `dispatch`'s generic timeout/error handler at `:253`. That calls unconditional `close::refuse` at `:264`. The existing helper contract explicitly limits `refuse` to pre-claim rejection (`handlers/close.rs:28`); post-claim failure must use `close_if_owner` (`:93`). A client replacing a slow/failed request can therefore lose its replacement and live updates. This violates P10 and repository Review-Proven Rule 2.

**Same lifecycle class, read/inferred (not independently race-injected):** live registry insertion/topic retention at `host_registry.rs:538` occur after the lifecycle lock has been released at `:535`. A concurrent CLOSE/replacement/connection cleanup can retire the map token before the old task registers/retains its topic. The old task then fails the send-owner check and returns without owning that residual registration. Existing `close.rs:66` says map token, index, topic retention and terminal frame must share the lifecycle lock. Timeout cancellation can also interrupt these awaited lifecycle effects. Fix the ownership class, not only the observed error branch.

**Fix:** retain ownership through post-claim failures and timeouts, and perform map/index/topic lifecycle transitions under the existing lock with cancellation-safe cleanup. Add deterministic same-ID old-error and old-timeout cases plus CLOSE/replacement during topic setup; assert replacement remains usable, no late old frames, and topic/index ownership cleans up. Reuse existing helpers; no new subscription framework.
