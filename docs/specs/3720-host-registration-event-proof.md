## 1. Existing foundation and narrow design choice

**Read.** `crates/buzz-db/src/store/paired_hosts.rs:72–85` starts a community-admitted writer transaction, takes the existing admission/restriction lock and bounds lock waiting. `:192–233` selects an exact claim and atomically inserts its ack and active binding. `:264–306` requires an unrestricted direct owner member, with configured owner allowlisting, while the host is restriction-checked rather than made a relay member. `schema/tables/public/paired_host_bindings.sql:14–16` supplies a unique live/fenced `(community_id,host_key)` index. Keep these boundaries.

**Read.** Current normal AUTH performs membership checks (`crates/buzz-relay/src/handlers/auth.rs:726–779`), the final writer recheck and connection binding (`:860–927`), and optional default-channel auto-join (`:977–994`). `AuthContext` carries normal permission scopes and an optional agent owner (`crates/buzz-auth/src/lib.rs:89–105`), not a host generation capability. An empty scopes vector alone is insufficient: every handler that checks only authentication must also be excluded from host mode.

**Read.** Existing membership invitations are real community-admission authority: only relay owners/admins mint them (`crates/buzz-relay/src/api/invites.rs:348–365`), and redemption inserts role `member` (`crates/buzz-db/src/store/relay_invite.rs:614–615`). They remain the path for admitting an otherwise ineligible human owner. They are **not** used to grant broad membership to hostd. A host console invitation establishes possession of a machine; it is not a community invite.

**Proposed choice.** Use the existing root WebSocket and standard `AUTH`, `EVENT`, `OK`, `REQ`, `EVENT` delivery, `EOSE`, `CLOSE`/`CLOSED` frames. Keep `paired_host_bindings` and `paired_host_events` as the single authoritative registry/transcript, with a normal-event adapter. Do **not** also insert these private events into the generic `events` table. Main already has special ingest dispositions outside public event storage (for example product feedback at `handlers/ingest.rs:2685`); this is an explicit private-kind handler, not ordinary chat persistence obtained merely by adding a constant.

The existing private store supplies the authorization policy. Normal WS supplies framing, challenge authentication, connection/resource lifecycle and subscription mechanics. New code must bridge them; no code-savings claim follows automatically. The supported fork extends upstream's product model deliberately; a stock relay remains unsupported.

## 3. Admission/bootstrap contract

**Proposed; unavoidable new authority is narrowly scoped host-session admission.** Operator enabling v2 authorizes this capability, just as enabling the old private paired surface authorized nonmember host access. It does not authorize owner-delegated community membership.

1. O authenticates normally and must be a direct eligible member under the existing owner policy. O posts a valid v2 `pair-claim` targeting H/G. Commit only a candidate, not a host reservation or binding. Keep existing bounded candidate quotas (`paired_hosts.rs:149–190`).
2. H connects to the same WS listener, receives the ordinary challenge, and signs NIP-42 with the ordinary `relay`/`challenge` tags plus exactly one `host-registry` tag containing `"2", G`. The complete AUTH signature binds that tag. Reject duplicate/unknown scope forms and combinations with owner-delegation credentials; never reinterpret a failed host-mode auth as normal auth. Reuse signature/challenge/time validation (`buzz-auth/src/nip42.rs:47–87`), then apply the new scope verifier.
3. Admission requires exact H/G/T targeting by a retained eligible claim, or exact H/G/T membership in an existing binding. Before a claim exists, deny uniformly; hostd retries with bounded backoff. Never accept arbitrary pre-auth REQ, EVENT, COUNT, or generation enumeration. For an unbound candidate, require an unexpired claim for first pairing; the only post-expiry exception is the bounded ack-retry recovery described below.
4. Add a **connection capability separate from ordinary AuthContext scopes**, e.g. `HostRegistrySession {community, host, generation, mode}`. No `MessagesRead/Write`, `UsersRead/Write`, admin scopes, default-channel auto-join, verified-profile publication, agent-owner materialization, NIP-OA fallback, or membership/allowlist insertion. Host-mode remains constrained even on an open relay or if H independently happens to be a member. A separate normal connection can exercise only rights H independently already has; registration grants none.
5. Bind the session before the final restriction check, then repeat the authoritative scoped check and cancellation check before committing auth, preserving the existing removal-vs-auth ordering at `handlers/auth.rs:860–927`. Carry host/owner restriction dependency in connection tracking for disconnects without setting `agent_owner_pubkey` or writing an agent ownership link. Every host operation and delivery rechecks the current DB authority; the connection capability is a scope ceiling, not a cached grant.
6. At the connection dispatch boundary, host-mode accepts only v2 registration EVENT operations, v2 protected REQ shapes for its exact G, and CLOSE. COUNT, search, negentropy/sync extensions, normal REQ, profiles, channel events and any unknown message fail closed. Gate both normal handler entry and specialized adapter, including already-open subscriptions. Ordinary member connections use existing generic admission plus registration operation authorization.

Owner membership removal or restriction makes normal registration reads/writes unavailable; it never transfers ownership. H may retain a **recovery-only** scope to learn its own immutable binding state and submit `unpaired`, even when O has been removed. Return no old payload/history/labels in that state. H's own ban denies relay access as today; local revocation still works and waits durably for permitted reconciliation. This narrowly extends the old removed-owner tombstone exception (`paired_hosts.rs:273–278`) to safe WS recovery, rather than relaxing all reads.

## 4. Signed mutation envelope and operation matrix

**Proposed v2 peer envelope.** Use NIP-01 signatures and NIP-44 v2 encryption to the exact peer. Strictly parse bounded JSON, disallow duplicate/extra fields and tags, and use canonical lowercase identifiers. Required signed tags, in canonical order:

```text
["v","2"], ["community",C], ["o",O], ["host",H], ["g",G],
["p",recipient], ["op",operation], ["i",operation_id],
["prev",parent_event_id_or_dash], ["expiration",unix_seconds]
```

`operation_id` is 32 random bytes persisted before the first send; use the same signed bytes/event ID for a retry. `-` is the sole absent-parent encoding. Reject unknown operations, `h` channel tags, contradictory recipients, extra route fields, or unsigned JSON sidecars. Bind the authenticated connection signer to the event author. The signature already commits to content/ciphertext; a second ciphertext hash is unnecessary. The decrypted body carries `v,community,owner,host,generation,op,operation_id,parent,expires_at` and operation-specific fields; compare all duplication exactly against trusted local scope and signed header. No proof, label, runtime details, path, key, or credentials in tags.

| Operation | Author → recipient | Parent / payload | Authoritative transition |
|---|---|---|---|
| `pair-claim` | O → H | `-`; private proof | Candidate only; no reservation. O must be an eligible direct member. |
| `pair-ack` | H → O | Exact selected claim ID; inner claim ID | Binding ACTIVE only after existing owner/host/claim checks and uniqueness transaction. |
| `status-query` | O → H | Accepted ack ID; fresh nonce | Readiness request only, not management authority. ACTIVE only. |
| `status` | H → O | Exact status-query ID; same nonce, ack ID, local active/revoked state and monotonic sequence | Authenticated freshness proof; does not create/change ownership. A short optional private label may be carried. No runtime catalog or agent placement in this slice. |
| `unpair` | O → H | Accepted ack ID; restrictive intent | ACTIVE→FENCED at relay commit; queued for offline H. |
| `unpaired` | H → O | Accepted ack ID; restrictive local completion | ACTIVE/FENCED→DEAD; never reactivates. |

Retain P0's 600-second invitation, independent 256-bit proof/generation, exact local expiry/monotonic check, constant-time proof digest, five distinct wrong-proof attempts, and atomic proof consumption plus ack outbox. Existing implementations are `paired_host.rs:110–159,475–555` and `buzz-hostd/src/store.rs:150–291`. Make codecs explicitly version-aware; do not weaken v1 parsers to accept v2.

An ack created by H while the invitation was valid may be retried for the existing bounded 24-hour delivery allowance (`paired_hosts.rs:192–214`). The relay can inspect the signed creation/expiry/parent and matching retained claim; only H can certify local proof consumption. It cannot decrypt or independently verify that secret. A fresh claim/first host consumption after expiry must fail. After that retry window, exact already-committed ack replay can confirm historical acceptance; an uncommitted ack requires local restrictive reset/re-enrollment, not resurrection of G. A fresh device treats historical ack as ownership evidence, not current host availability, until status answers its fresh nonce.

Idempotency keys are `(T,G,author,operation_id)` with exact event ID/content equality. A changed event under the same operation ID conflicts. Existing event-ID dedupe remains (`paired_hosts.rs:123–141`); add operation-ID lookup through existing `request_id` only for v2 registration records, with a documented version distinction. No phase/request row is created for registration. Since mutations already serialize under the community lock, the proof can enforce this lookup without new tables or migration history edits; index/performance changes, if needed, go through #3730. Every retry reauthorizes before returning a prior result.

Keep one active/fenced owner per `(T,H)`, immutable parties for G, and permanent dead-generation evidence. Claims from two owners can coexist; only the host's durable proof-consumption decision selects one, and a malicious/misbehaving host cannot create two simultaneous bindings. Hostd also enforces one local community/owner grant. Re-enrollment requires the old grant to be dead and a new local G/proof; neither labels nor timestamps select an owner.

## 5. Protected REQ, discovery and live delivery

**Chosen read mechanism: ordinary authenticated REQ plus a small versioned read adapter.** A signed query event is unnecessary: the socket already establishes the reader. Old NIP-98 sidecars mattered for mutation authority; that does not imply subscription filters need signatures. Plain REQ time filters alone cannot carry the current binding projection, complete page, commit high-water or scoped continuation. The adapter supplies those existing private-store semantics without a second query-event ingress/persistence subsystem.

The v2 client sends one strict filter, parsed before generic SDK filter deserialization so unknown extension fields cannot silently disappear:

```json
["REQ","hosts-1",{
  "kinds":[43103],"#p":["<authenticated-reader>"],
  "host_registry":{"v":2,"view":"hosts","nonce":"<32-byte-hex>","cursor":null}
}]
```

`host_registry` has an exact closed schema: `v,view,nonce,cursor`, plus `generation` for scoped views and `event_id` for evidence. Views are `hosts`, `history`, `binding`, `offers`, `evidence`, `messages`, `live`. No caller-selected owner, tenant or impersonated recipient. Owner identity always comes from auth. Host-mode requires exact session G and cannot use hosts/history. `live` uses exact G for a host; an owner can watch their registry across G. Mixed filters/kinds, unsupported options, missing extension, search, ordinary limits/time paging, or an incorrect `#p` are rejected for this private-kind request. This is a documented fork REQ extension, not a claim of stock client compatibility.

Each finite REQ returns one normal EVENT containing a **relay-authored** 43103 `registry-page`, followed by EOSE. These are generated read results, not durable mutations: reject all inbound client `registry-page` operations; never write pages to either event table or fan them out globally. Required signed tags: `v,community,p,op=registry-page,q=nonce,view`, and G for scoped views. Its NIP-44 content, encrypted relay→reader, repeats those fields and carries current state, summary/evidence, high-water, `next_cursor`, and `complete`. Client verifies the relay key obtained from the selected tenant's authenticated NIP-11 metadata, nonce, scope and page schema before use. EOSE without a valid correlated page is a protocol failure, not an empty registry. This small reply type is necessary because original claim/ack events alone do not state current relay FENCED/DEAD state or page completeness.

- **hosts/history:** reuse `read_paired(Read::Hosts)` owner checks and generation ordering (`reads.rs:80–106`). Return up to 16 compact summaries with `(G,O,H,state,claim_id,ack_id,tombstone_id,latest_status_id)` and no private label in cleartext. History includes dead grants. Active and historical bounds remain 32/512 per owner (`paired_hosts.rs:217–219`).
- **binding:** reuse current projection under its writer lock (`reads.rs:252–302`), returning immutable references, state and high-water. Evidence is fetched separately so a page cannot grow with nested envelopes.
- **evidence:** fetch one exact retained selected claim/ack/revocation/status event after participant and generation authorization. A known event ID never grants access. The result contains the exact signed peer event as JSON, not a reconstructed/re-signed replacement.
- **offers/messages:** reuse exact-G authorized selection, commit sequence and retention-floor behavior (`reads.rs:54–75,108–148`). At most 100 compact event references per page; retrieve bounded evidence individually. A pruned cursor is explicit `resync_required`, never successful empty history. Offers do not reveal other hosts/owners outside the authorized candidate set.
- **live:** register before the finite snapshot under existing subscription lifecycle ownership (`handlers/req.rs:1555–1605`). Deliver relay-authored encrypted `registry-change` notifications to each authorized subscriber, containing G and committed sequence/high-water only. A change is an invalidation hint: refetch the protected projection; it is not authority to activate or launch. No chat/push/workflow effects. The signed page/change constructors share the same read authorization, and private delivery uses the existing guarded send seam, not generic p-tag-only permission.

Cursor authenticity is reused/extracted from `api/paired_hosts.rs:145–207`, bound to T, reader, view, G where applicable, position, snapshot high-water and a short expiry. It is not an authorization credential. Reauthorize every page on the writer. Capture the owner-scoped high-water with the first page under the admission lock; if relevant binding state changes while a list is paginated, explicitly resync instead of silently assembling a mixed complete list. Retry at most three whole snapshots per refresh, then report unavailable/stale and preserve cached data. No infinite retry loop.

For a second desktop: authenticate O from the same owner identity, subscribe live first, obtain all complete list pages, fetch selected claim/ack evidence for each G, verify dual consent, fetch binding state, then challenge each active H with a fresh status nonce. No copying the first desktop's journal or private console proof. Local journals are outboxes/caches; never list authority. Show offline/stale separately from revoked; an inactive or unavailable host does not disappear merely because it cannot answer.

**Delivery and restart:** persist mutation/transcript and binding transition atomically; return OK only after commit. Reuse paired rows/seq as the durable catch-up source. Redis/local notification is post-commit and best effort; lost notification is repaired by a bounded periodic authoritative resync (60 seconds while connected), reconnect resync, and before any future control operation. No second durable event log/outbox is required for registration correctness. Actual live fanout must recheck T/reader/G/current restrictions on the sending node (`handlers/event.rs:305–319,359–386`); cached subscription match is insufficient. A delivery authorized before revocation may already be in flight; after the revocation commit, new authorization checks deny ordinary delivery. Existing agents are unaffected by registration state changes in this slice.

**Generic reads:** new records remain absent from generic `events`, FTS, feeds, exports and count paths. Explicit v2 queries through generic HTTP `/events`, `/query`, `/count` are unsupported in this proof and fail closed; do not partially accept an operation without the scoped context. ID-only/kindless/mixed-kind/search/count queries and ordinary wildcard subscriptions must return no private record or existence hint, including if someone guesses an ID. Add defense-in-depth kind handling at generic result/fanout seams, not a loose addition to `P_GATED_KINDS`: the owner/host/generation policy requires a DB lookup. Main's result gates are useful patterns (`handlers/req.rs:1718–1740`, `handlers/event.rs:204–218`), not equivalent authorization.

## 6. Revocation, bounds and recovery

Relay revocation linearizes at the existing FENCED/DEAD transaction (`paired_hosts.rs:235–255`). A delayed status or ack must not change a fenced/dead binding. Restrictive unpair/tombstone retries remain available under a separate bounded recovery allowance. Historical proof remains fetchable only to presently authorized participants; removed-owner host recovery reveals only its own minimal binding state and accepts restrictive reconciliation. Never reopen generic history merely to make that path work.

Hostd persists local revocation before acknowledging it; keeps the exact tombstone in its outbox across restart; does not issue a new invitation while the old grant is locally active. Owner removal or unavailable relay disables new management permission, not running conversational agents. This registration proof neither stops services nor claims instantaneous cancellation on an offline machine. Future provisioning/lifecycle operations must independently prove current authorization; #3738/#3739 retain that obligation.

Proof defaults: 600-second invitation; 30-second skew; status query/response lifetime at most 60 seconds; v2 peer event at most 16 KiB serialized and decrypted payload at most 8 KiB; page plaintext at most 24 KiB and serialized EVENT frame strictly below 60 KiB, checked after encryption/padding. Keep the existing 64 KiB connection-frame ceiling; never increase it to accommodate page nesting. Lists contain references; evidence has one bounded event. Pin maximum tag count, tag value lengths, query cursor length and JSON depth in codec tests. These are proposed v2 registration limits, not changes to v1's 32/16 KiB bounds (`paired_host.rs:25–27`).

Preserve candidate/owner/binding quotas already enforced in the writer, shared tenant/principal/source budgets, bounded crypto concurrency and distinct recovery budget from the old adapter (`api/paired_hosts.rs:298–321,336–396`). Apply WS frame/auth/rate limits on the relay itself; direct listener and an ordinary reverse proxy must behave safely when many legitimate clients share the proxy's TCP address. Authenticate before granting any known-principal allowance; no trusted forwarded header shortcut. Reserve one of the per-connection bounded registration work slots for restrictive recovery; test saturation explicitly.
