## P1 — real same-host Save is missing

**High; read evidence, not newly exercised:**

1. Profile Edit prefers the linked definition (`UserProfilePanel.tsx:400`), whose submit first updates the persona and then its managed record, finally reporting “Updated” (`UserProfilePanelPersonaSubmit.ts:78–103`). Model/instructions/harness are propagated locally (`UserProfilePanelUtils.ts:286–331`). Main's exact contract is already **save now, most runtime settings take effect on next spawn** (`desktop/src-tauri/src/commands/agent_models_update.rs:137–151,179–184,200–218`); access changes have a separate stop/publish/restart boundary. Read comparison: locally available `origin/main` at `e3a0f3d59dfd08696cff80badb2d80d9a5096a61` carries the same contract at `agent_models_update.rs:137–151` (`git show`, no fetch or checkout). This is not a hosted apply operation.
2. Existing wire `Action::Deploy` explicitly supports create/update at the same placement (`crates/buzz-core/src/host_deployment.rs:169–176`). Relay admission binds owner/host/generation and exact expected revision; it preserves cleanup fencing (`crates/buzz-db/src/store/paired_hosts/deployment.rs:100–110,139–142`). **No new Update wire verb is needed.**
3. Owner continuation deliberately accepts only `needs-login`/`failed`, not an applied deployment (`crates/buzz-paired-owner/src/deployment/continuation.rs:105–113`). It permits only a selected-model snapshot delta (`:214–222`). Desktop recovery independently rejects other record changes (`desktop/src-tauri/src/commands/agents_hosted.rs:395–400`). Removing either guard alone would violate the recovery contract.
4. Host preparation accepts a newer revision of the same identity, but an active unit must have byte-identical configuration; changed active configuration returns `unit busy` (`crates/buzz-hostd/src/user_service.rs:229–250`). The controller stages → prepares → starts (`crates/buzz-hostd/src/deployment.rs:462–499`); it does not provide an implicit stop-and-replace transaction.
5. Ordinary Desktop Start rejects registered-host lifecycle actions (`desktop/src-tauri/src/commands/agents.rs:1038–1039`). Thus “saved, applies next start” is also unimplemented today. `VISION_REMOTE_AGENTS.md:61` supports next-body application, but is not proof that this fork has implemented it.

**Inference grounded in those guards:** safe same-host editing needs native desired-configuration materialization/recovery plus a defined application boundary. Merely threading hosted discovery into Edit would leave local and running state divergent and can make recovery fail with “Saved setup configuration changed.” Do not loosen continuation/recovery guards or invoke Cleanup to restart; Cleanup permanently fences resurrection.

### Decision P1: when does Save take effect?

| Option | Concrete user contract | Prerequisite / tradeoff |
| --- | --- | --- |
| **A — complete main's existing Save/next-spawn contract (recommended)** | Ordinary Edit saves the same agent's harness/model/instructions; UI says “Saved; takes effect on next start.” Running configuration stays accurately reported. Explicit Start applies the saved configuration on the same host. | Adapt existing main update/materialization and revisioned Deploy to registered-host Start, including recovery. No new settings framework or automatic interruption. Cannot be claimed until Start actually consumes the saved settings. |
| **B — Save and restart now** | Explicitly labelled action applies settings by replacing the running body on the same host, retaining key/history. | Requires reviewed stop confirmation, in-flight-work behavior, replacement and failure recovery. More lifecycle scope; cannot be obtained by ignoring `unit busy`. |
| **C — narrow release first** | Ship truthful status and normal launch now; hosted configuration is temporarily inspectable with “Changes to this hosted agent cannot be applied in this version.” No successful Save for execution settings. | Temporary limitation requiring a conductor/user ruling, not the final editable product contract. Does not fulfill the requested same-host Edit acceptance. Route A or B next. |

Recommendation: **A, extending main's existing contract through the existing host deployment machinery; C only if an immediate partial canary is wanted.** This is an integration prerequisite, not a proposal for a new management mechanism. Do not silently select C, permanently disable editing, or rebrand local-only persistence as an applied save. The safe default while the ruling is pending is to implement F2/F3 and hold the hosted Edit release.
