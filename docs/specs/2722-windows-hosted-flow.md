## Endpoint and non-goals

The ordinary Windows Add Agent form selects a verified registered host and its supported installed harness, prepares one new identity with `PendingLogin`, displays durable setup status and operator-local login guidance, explicitly refreshes models with a new pending operation, selects a returned ID through the existing picker, and submits `Selected` using the same identity and placement. Closing/reopening or retrying continues that setup. Preparation does not promise launch; the installed offline policy can truthfully refuse Selected execution.

Keep shared definition/configuration validation, native key generation and NIP-OA attestation, managed record/profile/channel paths, ACP, and remote execution labeling. Host creation remains disabled unless native `BUZZ_NATIVE_HOST_DEPLOYMENT_V1=1` is explicitly set for isolated source testing; renderer state cannot enable it. Registration/Add Host remains discoverable independently.

No live relay/netcup/provider/real pairing or existing Claude/Grok/Scout access. No general Start/Stop/Delete UI, remote authentication protocol, provider-login browser action, installer/adoption, HTTP retirement, main catch-up, polling framework, online policy, schema/table/event kind/query protocol, or new durable coordinator. N1 (#3719), actual native login/service acceptance (#3722), Windows/human acceptance and later rollout remain separate. This extends the already accepted private relay deployment path; it does not reinterpret the external-provider vision or give the desktop a direct host channel.

## Contract: native ownership and renderer data

Add a small Windows native hosted bridge adjacent to `agents_hosted.rs`, registered under the same Windows command gating as paired hosts. Function names may follow existing command conventions; responsibilities are fixed:

1. **Catalog/readiness read:** expected community + owner + host/generation narrow the captured native session. Revalidate registration/current permissions and open fresh private Status via Management. Return feature-disabled/unsupported/unavailable/stale/revoked distinctly where evidence supports the distinction, approved catalog revision, expiry, installed runtime IDs, and canonical main metadata. Do not equate connection error/missing status with Offline. A revoked registry row can say revoked; denied private reads alone cannot infer the reason.
2. **Setup list/read:** bounded native enumeration of existing `deployment_intents` for the captured community/owner (existing cap 1024), grouped by exact agent+scope, plus managed record summary. Decrypt/validate through existing intent restoration. Return only public setup coordinates, saved definition ID, display name, phase/status, and validated observation. Initial phase-zero intents remain discoverable even if record materialization never finished. No WebView private key, ciphertext, auth tag, arbitrary snapshot, launch payload, login output, executable path or environment. The ordinary create response contains a private key today; the hosted IPC must explicitly project a secret-free response instead of serializing it unchanged (`agents.rs:914`).
3. **Prepare/resume:** use main create phases for a new definition-backed identity and the existing restore branch for its retained operation. Before enabling the first Prepare, obtain one native-generated opaque 32-byte setup token for that new form draft, excluding the reserved cleanup prefix. This token **is the existing initial operation ID**, not a new persisted field or reservation table. Keep it stable in the mounted draft; freeze submitted inputs and send the same token on duplicate calls/retries. Token allocation alone mints no agent and has no durable effect. The native journal and signer remain authoritative. Return retained-setup information on publication/admission failure so the UI offers resume, never another create as an automatic retry.
4. **Check status / retry exact / refresh models / launch:** use the operation rules below, returning the same sanitized setup shape. Reads and explicit actions are finite; no persistent subscription or automatic polling loop. One-shot UI expiry invalidation is allowed and performs no network request. A subsequent explicit action always rechecks native freshness.

Runtime metadata joins **installed runtime ID → approved harness key → existing Rust canonical builtin/preset definitions**. Factor a pure metadata constructor if needed so local and hosted projection share the same facts; do not invoke local command resolution/auth probes with a fake path. Grok remains a preset, not a new KnownAcpRuntime. The hosted projection carries static capability/label/argument facts while host Status supplies installed availability; local binary paths, local login hints and local auth status do not become host evidence. Unmapped/unknown entries are explicitly unsupported. More than one installed ID can map to one harness: retain the chosen installed ID in setup state and distinguish entries, rather than collapsing them by label.

Renderer caches/requests use full community, owner, enrollment, host, agent (when allocated), runtime, catalog, operation, revision and action correlation where applicable. Account/community/host/runtime change, close/unmount, revoke, a newer action, or expired evidence clears launchability and fences late completion. Scope generation must be checked after each native network wait and before store/publication effects. A saved selected ID may remain visible as an unavailable value; no cached success grants permission or silently chooses another model. No new module-global cache is needed.

## Contract: exact durable operation transitions

Reuse `Intent { protected, event, materialization, phase, result }` and existing main records. Permit narrowly validated nonzero-revision Deploy intents alongside revision-zero create; retain compatibility with existing rows. Do not simply remove the zero check and accept an arbitrary renderer revision. A native continuation must prove same agent/identity/auth-tag/scope/backend/runtime and matching saved setup before creating its next immutable intent. `ProtectedCreateIntent::validate` is create-specific (`host_deployment.rs:384`); keep that invariant explicit. A small separately named core follow-on validator beside it is expressly in scope if needed, with affected core tests; this permits no relay/schema expansion.

| Transition | Required durable behavior |
|---|---|
| New preparation | Current status and accepted configuration first. Main mints one key/attestation. Seal exact PendingLogin command + keyless recoverable main snapshot in existing protected journal before record/publication/dispatch. Initial expected revision 0. Main save then profile publication advance phases 1 and 2; exact admission advances 3. |
| Reply loss / retry / reopening | Look up retained intent; restore the same key/record/definition and exact event bytes. Repair incomplete save/profile phases idempotently. Do not rerun definition creation, avatar upload, or mint on retry. Query the original operation before interpreting expiry or missing reply. Existing terminal receipt is immutable; same-op retry cannot refresh models. |
| Explicit Refresh models | After the prior setup operation is reconciled and current authority/status confirmed, allocate a new PendingLogin operation for the same identity/runtime/unit/HOME. Use current **admitted placement revision**, including after a failed command, not only the last successful applied revision. Persist new intent before record effects/send. Keep stable saved configuration; no new persona or key. Pending/unknown work is resolved by Check status or exact retry, not automatically superseded. Applied conversation and cleanup states cannot refresh. The host retains its final busy/inactive guard. |
| Launch selected model | Require current preparation result, current status/catalog/mapping, fresh observation, login Succeeded and Available models, with selected ID present exactly. Allocate new Deploy(Selected) for same placement at current revision. Persist updated main model through existing record save under lock and protected recovery snapshot before send; preserve public identity/profile/channel state. The protected snapshot makes save/publication prefixes recoverable, not an unjournaled pre-send mutation. Host re-probes and strict ACP startup can still reject; display that outcome truthfully. |
| Expired unadmitted operation | A verified original operation read must show it absent before replacement. Recover original identity/config, then explicit new operation at revision 0; no unit has yet been established. Its first accepted operation establishes the stable unit. If admission is uncertain, retain blocked/pending recovery; do not guess zero. Once placement exists, every later operation retains the returned unit. |
| Expired admitted / stale observation | Query existing operation/placement under current permission. Keep receipt as historical; do not extend expiry or mutate signed bytes. A terminal preparation can take explicit new pending refresh at current revision; an unresolved pending command stays unresolved until reconciled. Failure/expiry never deletes identity or native state. |

Current-operation reconciliation is load-bearing: an operation query can return its historical event/result **and a newer placement revision**. Require returned event == saved signed event, matching result authority, and placement revision == operation.expected_revision + 1 before treating that operation/observation as current. `Management::observation` already validates result/config/time/current read permissions, but does not itself compare the placement revision; make that comparison in the same production owner/bridge read path. Older receipts may be shown as history only. If a newer local intent exists, resolve that intent; do not regress to the older successful one. If another controller advanced placement and there is no matching local intent, show conflict/unavailable and stop; do not invent a new query or reconstruct a key from remote data.

Serialize same-agent setup writes through existing native store/session locking and existing SQLite immediate transactions. Move the same-token lookup/insertion check into the existing immediate-transaction boundary: only its winning intent may proceed to main record/profile/send effects. A duplicate same-token caller restores that winner, or rejects conflicting frozen inputs; it never saves or publishes its losing candidate. The main phases may transiently generate a discarded candidate key before insertion; this contract requires exactly one **durable/external identity**, not exactly one RNG invocation. Distinct deliberate new-draft tokens denote distinct creates and are never deduplicated by name. A crash before intent commit leaves no saved agent; a crash after commit is recovered by scoped intent enumeration. Recovery orders an agent's existing intents by their bound revision, resolving competing candidates against exact admitted relay bytes; wall-clock timestamps or a preferred successful receipt never choose the winner. Do not replay the original create snapshot over a later saved model. Do not hold a synchronous lock over network waits. Relay CAS remains the final placement arbiter. Existing intent cap stays bounded: capacity exhaustion is an actionable retained-state error, not eviction or automatic garbage collection.

The root create intent's protected record carries the stable definition ID and identity; continuation discovery is exact-key based, never name matching. A deliberate second Add Agent action can create another agent; a retry/resume cannot. The shared submit handler must acquire a synchronous in-flight latch before avatar upload or definition save (React pending state alone is not a same-tick guard), retain the resulting definition ID for this token, and reuse it on retry. Duplicate submissions therefore cannot create duplicate definitions or repeat avatar side effects before reaching native identity protection. Keep incomplete definition-only saves distinct from an allocated hosted setup. Optional target-channel attachment uses the ordinary membership helper with `ensureRunning:false` for registered hosts (`channelAgents.ts:177`); retry attaches this same identity. Channel failures stay visible/retryable and cannot fall into native local Start or provider deploy. No new durable channel-work queue is introduced; after app restart the normal existing-agent channel affordance remains recovery.

## User-visible truth and configuration behavior

Choosing a host loads its metadata, then the ordinary harness selection reflects that source. Loading/error/unsupported/stale/revoked are visible and block preparation; registration alone never enables it.
- Prepared setup displays “Needs login” only when the observation supports it; login success with no usable model is “Models pending/unavailable,” not verified subscription readiness. Show login outcome and model outcome as separate facts. Empty, unsupported, network-disabled, timeout/execution/invalid-output/oversized, expired and denied reads keep their distinctions. Unknown host reachability is not Offline; conversational Online/Away/Offline remains the existing relay presence reader.
- Guidance identifies the exact prepared agent and host. Tell the operator to complete native login on that host in this new agent's prepared context, then press Refresh models. If showing the fixed helper invocation, obtain its validated unit from the current native operation read and use the existing `buzz-host-activate --login UNIT` mechanism; do not execute it from Windows or expose login URLs/codes/output. Under shipped offline policy say networking is disabled; no install/network-policy workaround is offered.
- “Check status” reads current evidence; “Retry” resends exact retained bytes; “Refresh models” creates a new pending operation. Labels must not conceal their different effects. Show preparing/admission pending, publication failure, failed application, deployment applied and conflict separately. Applied is service application, not chat readiness or Online.
- Preserve main picker labels and opaque IDs, with only fresh returned options actionable for host selection. No Custom model, bundled provider list or Windows cache fallback grants hosted launch. On expiry keep the selected value visible but disable Launch until explicit refresh and revalidation.
- Cloud + “Runs on <registered label> · <short host key>” describes placement in the existing summary. Scope, not label, is identity; use short key fallback if label unavailable. Preserve the shared “Not managed on this device” predicate unchanged: a hosted agent with a local managed record does not qualify (`docs/agent-management-provenance.md:3`). Presence, management provenance and placement are separate facts. No per-row directory subscriptions.
