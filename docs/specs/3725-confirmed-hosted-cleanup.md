## F1 — retain and reconcile one Cleanup

**Severity:** H1. **Depends on:** existing transport/journal only. **Files:** `crates/buzz-paired-owner/src/deployment.rs`, `deployment/continuation.rs`, `deployment_tests.rs`; one focused sibling is allowed for file-size policy, not a new subsystem.

1. Resolve target from the original protected intent and active native signer: full community/owner/host/generation/agent, exact placement unit and current admitted revision. `Management::operation` already authenticates a nonce-bound relay reply and checks exact admitted event bytes, state/result agreement and `expected_revision + 1` ([continuation.rs:42](../../crates/buzz-paired-owner/src/deployment/continuation.rs#L42), [247](../../crates/buzz-paired-owner/src/deployment/continuation.rs#L247)). Reconcile latest same-agent intents and competing pending operations; never pick a label or renderer revision.
2. For an admitted current Deploy (pending, failed, needs-login or applied), retain `Command::Cleanup {}` at its admitted revision, including when no applied revision exists. Do not finish/retry the Deploy or rematerialize/profile-publish merely to become eligible for Cleanup. Reconcile unknown follow-ons first; admission uncertainty cannot be guessed away. A pending Deploy may be superseded by restrictive Cleanup using existing relay CAS.
3. Use the existing `Intent` row and encrypted materialization. Bind a minimal native-only predecessor reference in that snapshot to the exact retained Deploy supplying display/recovery metadata, if needed; validate its scope/agent and command, never accept it from the renderer. Keep the original encrypted Deploy identity for unresolved recovery. No second plaintext key or new persistence layer. Cleanup phase semantics must be explicit: retained before send, dispatch-ready without main creation/publication effects, admitted after relay evidence, locally finalized after deletion. Reuse phases 0–4 with action-specific interpretation; do not run Deploy phase effects for Cleanup.
4. Serialize duplicate admission decisions through the existing SQLite immediate transaction: recheck the latest same-agent journal inside the transaction and return the retained Cleanup winner. Seal once with `wire::seal_command`; it **derives the Cleanup operation ID after encryption**, so persist and return that final ID, not the candidate ID ([wire.rs:184](../../crates/buzz-core/src/host_deployment/wire.rs#L184)). Concurrent Delete/setup clicks, lost replies and restart reuse exact event bytes. A UI latch is not the concurrency boundary.
5. Cleanup needs active session, current binding/read permission and exact current placement evidence, not fresh catalog, installed runtime, native readiness or models. Connect/query through existing guarded Management without forcing native `open`'s status/runtime checks ([agents_hosted.rs:157](../../desktop/src-tauri/src/commands/agents_hosted.rs#L157), [260](../../desktop/src-tauri/src/commands/agents_hosted.rs#L260)). Relay unavailability/denial means no new authority and no successful deletion; pending journal remains recoverable.
6. Reconcile before checking expiry. Current `cleaned` plus valid receipt completes even after command expiry; `cleanup-pending` remains pending. Exact retry never reseals. If an expired never-admitted Cleanup must be renewed, explicit Delete/Retry may retain one replacement only after a fresh proof of the original predecessor's still-current revision and absence of competing admitted work. An admitted terminal `Failed` Cleanup may be replaced only against its proven current revision. Reuse existing content-bound replacement semantics; new operation is an explicit renewal, not another logical delete. Preserve the permanent local Cleanup fence through all renewal paths. Unknown or superseded evidence refuses; no automatic retry loop.
7. Before retaining any later Deploy, and before every old Deploy recovery/publication/dispatch, reject when any validated Cleanup intent exists for that exact scope+agent, regardless of its expiry, phase or host outcome. Hold the existing native store lock around local recheck/effects; transaction-recheck before owner writes. A stale Deploy already sent may race, but CAS prevents it overtaking admitted Cleanup; never treat a resulting conflict as deletion success. Keep retained Cleanup after finalization as the durable no-resurrection fence.

**Verify:** G1/G2 below. **Watch for:** dispatch's current expiry-state list lacks `cleaned`/`cleanup-pending` ([deployment.rs:426](../../crates/buzz-paired-owner/src/deployment.rs#L426)); non-Deploy restoration/listing must not drop the only recovery affordance. Preserve the create-only validator; do not relax `ProtectedCreateIntent::validate` into generic authority ([core:402](../../crates/buzz-core/src/host_deployment.rs#L402)).

## F2 — confirm before main local deletion

**Severity:** H1. **Depends on:** F1. **Files:** native `commands/agents.rs`, `agents_hosted.rs`, `agents_hosted_commands.rs`, `agents_hosted_tests.rs`; a focused hosted cleanup sibling if needed.

Normal `delete_managed_agent` derives registered-host scope and retained operation from native saved state; renderer supplies only existing target identity and expected session coordinates where necessary. Its registered-host branch calls the same Cleanup coordinator as setup Delete. `force_remote_delete` must never bypass hosted confirmation. Avoid holding synchronous store locks over network awaits. Recheck captured session generation and exact record/backend/scope after every network wait and inside the final local mutation lock ([Session::keys:80](../../desktop/src-tauri/src/commands/paired_hosts.rs#L80)).

**The confirmation predicate is conjunctive:** freshly permitted relay operation read, exact retained Cleanup event bytes, current admitted revision/unit matching the target, host-signed/decrypted `Outcome::Cleaned`, full request equality (including action, digest, scope, agent, operation, expected revision and expiry), applied revision equal to expected+1, and relay state `cleaned`. Reuse `wire::open_result_body`, `DeploymentResult::validate` and `Management::operation`; a stored historical receipt, relay state alone, admission OK, elapsed time or offline presence is insufficient ([core:367](../../crates/buzz-core/src/host_deployment.rs#L367)). A revoked/denied read cannot authorize local forgetting even if host cleanup subsequently finishes restrictively.

Only after that predicate, reuse main `run_managed_agent_deletion` / record save / key deletion / pending tombstone and archive enqueue / cache invalidation ([agents.rs:1274](../../desktop/src-tauri/src/commands/agents.rs#L1274)). Extract a small shared finalizer if necessary; no parallel deletion implementation. Do not start/stop a local agent or invoke provider infrastructure for this target. Idempotently finish a partial local deletion on reopen/retry; absence of the record after an interrupted delete is not evidence of remote success by itself. Persist phase 4 only after local completion, retain Cleanup authority/receipt/fence, and never restore its predecessor record. A failure in local removal remains a visible retryable local-finalization failure, even when the host is already Cleaned. Retained encrypted historical intent material is not a claim that all historical key copies were erased.

Normal Delete returns success only when local removal completed. A pending result must propagate distinctly (an actionable existing error/result path is sufficient), so current caller follow-on channel removal does not run early ([useManagedAgentActions.ts:325](../../desktop/src/features/agents/ui/useManagedAgentActions.ts#L325)). Existing private intent listing must continue to expose pending cleanup when a saved record is absent; after phase 4 it can omit the completed row from active setup choices while preserving its fence.

**Verify:** G2/G3. **Watch for:** setup `Check`/`Retry` on an existing Cleanup may reconcile and finalize through this same helper; they must never fall through to `recover` or require models. The public sanitized DTO carries no key, auth tag, ciphertext, snapshot, host path or selectable unit.
